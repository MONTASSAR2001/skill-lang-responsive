Why we moved to event sourcing, and what we would do differently

Reading time: 6 minutes

The problem we had

For three years our order service stored only the current state of each order. That worked until finance asked a deceptively simple question: "What did this order look like last Tuesday at noon?" We could not answer it. Updates overwrote history, and the audit tables we had bolted on were incomplete, inconsistent and, frankly, a little embarrassing.

What event sourcing actually means

Instead of storing the current state, we store every change as an immutable event, such as OrderPlaced, PaymentCaptured or OrderShipped. The current state is simply the result of replaying those events in order. A projection is a read model that is rebuilt from the event stream whenever its schema changes.

Lessons learned (the honest version)

  • Do not model events after database tables; model them after things that happened in the business.
  • Snapshots are an optimization, not a feature. Add them late.
  • Version your events from day one, because you will change them, and you will regret skipping this step.

If you are considering the same move, our advice is simple: start with one bounded context, measure everything, and resist the temptation to rewrite the world in a weekend. Good luck, and may your replays always be idempotent.
